# Инструкции для ИИ-агентов

Эти правила относятся ко всему репозиторию и являются общим контрактом для Claude Code, Codex, OpenCode и других агентов, которые поддерживают \`AGENTS.md\`. Не дублируй их в других файлах: дополняй профильную документацию и правила по путям.

## 1. Цель и источники истины

Thaumic Horizons: Reforged — порт Thaumic Horizons из Minecraft 1.7.10 на современный Minecraft/NeoForge как дополнение для Thaumcraft 4: Reforged (TC4R).

- Поведение оригинала сверяй с \`reference/1.7.10/\`. Не восстанавливай механику по памяти, названию класса или догадке.
- Для старых ID предметов и блоков используй таблицу TC4R \`../thaumcraft-4-reforged/tools/data/id_map.json\`, когда она доступна. Не подбирай современные идентификаторы по семантическому сходству.
- \`docs/fidelity.md\` — реестр намеренных отличий и известных неполных портов.
- \`docs/verification.md\` — фактические результаты ручных и автоматизированных проверок. Отмечай пункт выполненным только после соответствующей проверки.
- \`docs/roadmap.md\` — план и обзор состояния; он может устаревать. При расхождении проверяй исходники, CI и актуальную verification-документацию.
- Текущие версии Minecraft, NeoForge, Java и мода бери из \`gradle.properties\`, а не копируй в новые инструкции.

Сохраняй логику, числа, рецепты, аспекты, исследования, названия и ассеты оригинала, если отличие явно не обосновано и не записано в \`docs/fidelity.md\`. Исправление бага оригинала допустимо, когда оно необходимо для корректной работы (например, потеря предметов, дюп, краш, рассинхронизация); задокументируй причину и ожидаемое поведение.

## 2. Обязательная проверка перед работой

1. Прочитай эти инструкции и ближайшие относящиеся к задаче инструкции по каталогам.
2. Проверь ветку, HEAD и \`git status\`. Не перезаписывай пользовательские или чужие незакоммиченные изменения.
3. Найди существующую реализацию, регистрацию, ресурсы, тесты и соответствующий код в \`reference/1.7.10/\`.
4. Проследи серверный и клиентский путь, сохранение/загрузку данных, синхронизацию и multiplayer-влияние там, где они применимы.
5. Составь узкий план изменений. Не переписывай соседние подсистемы ради косметики.

Если исходник, API или требуемое поведение не удаётся подтвердить, явно обозначь неопределённость и не выдумывай совместимость.

## 3. Архитектурные границы

В проекте существуют две независимые границы совместимости:

- \`platform/\` и \`client/platform/\` — различия версий Minecraft/NeoForge и клиентско-серверные платформенные API.
- \`dev.visfox.thaumichorizons.compat/\` — взаимодействие игровой логики с Thaumcraft/TC4R.

Правила:

- Игровая логика не должна напрямую зависеть от версионных NeoForge/Minecraft API, вынесенных в platform seams. Границы проверяются \`tools/check_seams.py\`.
- Внутренние классы и реализации TC4R используй только через \`compat/\` и его адаптеры.
- Прямой импорт TC4R допустим только для явно разрешённой публичной API-поверхности из \`THAUMCRAFT_API\` в \`tools/check_seams.py\`. Не добавляй туда класс автоматически ради удобства: сначала проверь возможность compat-интерфейса и обоснуй расширение.
- Реализация интеграции с TC4R и её mixin-цели находятся в \`compat/tc/\`; не размещай их в gameplay-коде.
- Клиентские классы не должны загружаться на dedicated server. Общие классы не должны импортировать \`net.minecraft.client.*\`, клиентские рендереры или клиентские NeoForge API.
- Регистрацию контента выполняй в существующих registry-классах и учитывай доступность соответствующих compat-возможностей.
- Не создавай второй источник истины для player attachments, item components, сущностей, рецептов, аспектов или исследований.

Подробности: [architecture.md](docs/development/architecture.md) и [tc4r-integration.md](docs/development/tc4r-integration.md).

## 4. Реализация и данные

- Следуй стилю соседнего кода; Java и Python — отступ 4 пробела. Не добавляй комментарии, которые лишь пересказывают очевидный код. Комментариями объясняй неочевидные ограничения, инварианты и причины обходных решений.
- Предпочитай существующие API, компоненты данных, attachment-ы, сериализаторы и compat-интерфейсы самодельным NBT-хранилищам и обходам.
- Не создавай \`ItemStack\` или компоненты, требующие bound data components, в статической инициализации или конструкторе регистрации до \`DefaultDataComponentsBoundEvent\`. Используй ленивое создание по существующему образцу.
- Следи за уникальностью ID регистрации, recipe keys, payloads, research keys и resource locations.
- Пути ресурсов должны быть lowercase. При переносе старых ассетов проверяй UV, размеры, alpha, parent/model/texture references, blockstates и фактическую регистрацию.
- Не заменяй отсутствующий ассет выдуманным placeholder-ом и не скрывай ошибку fallback-ом без явного решения.
- Для языков поддерживай существующие \`en_us\` и \`ru_ru\` и проверяй ключи по реальному коду, а не только по тексту.

Дополнительные правила для Java и ресурсов находятся в \`.claude/rules/\` и автоматически применяются Claude Code к указанным путям. Общие требования этого файла обязательны для всех агентов.

## 5. Тестирование и доказательства

Тесты выбирай по природе поведения:

- **JUnit 5** разрешён и предпочтителен для детерминированной логики: codecs, сериализации, преобразований данных, fallback-ов, чистых вычислений и изолированных контрактов.
- **NeoForge GameTest** не добавляй автоматически. Сначала докажи, что сценарий нельзя разумно покрыть JUnit или существующей проверкой; для добавления GameTest нужна явная необходимость и рабочая тестовая инфраструктура.
- **Seam check** проверяет архитектурные границы, но не корректность игровой механики.
- **Gradle build/test** проверяет компиляцию и автоматические тесты, но не доказывает работу механики в игре.
- **Dedicated server** подтверждает только те сценарии, которые действительно были запущены на сервере.
- **Client / multiplayer** подтверждают только фактически воспроизведённые визуальные, интерактивные и сетевые сценарии.

Не называй код проверенным в игре на основании компиляции, JUnit или CI. Запускай релевантные проверки и записывай точный результат в отчёте. Для поведенческих задач обновляй \`docs/verification.md\`; для подтверждённых отличий — \`docs/fidelity.md\`.

Базовые команды и границы CI: [building.md](docs/development/building.md).

## 6. Git, PR и параллельная работа

- Не делай merge PR, force-push, удаление веток/тегов, изменение branch protection, secrets, Actions permissions или настроек репозитория без прямого разрешения пользователя.
- Не переписывай чужие коммиты и историю. Не сбрасывай ветку и не удаляй незнакомые файлы для получения чистого состояния.
- Не коммить и не форматируй посторонние пользовательские изменения.
- Не добавляй co-author trailers, если пользователь явно не попросил.
- Коммиты — на английском, в стиле Conventional Commits (\`feat:\`, \`fix:\`, \`test:\`, \`docs:\`, \`refactor:\` и т. п.).
- При работе несколькими агентами каждому назначай отдельную область и по возможности отдельные файлы/ветки. Не допускай параллельной независимой правки общих интерфейсов, registry-классов, mixin-конфигурации и build-файлов.
- Перед интеграцией проверь diff каждого агента, конфликты, дублирующие реализации и совместимость общих API. Не считай отчёт субагента доказательством, пока не проверил его изменения.
- Не создавай PR только ради отчёта: сначала убедись, что ветка содержит законченное, проверенное изменение.

## 7. Когда задача завершена

Сообщи кратко и предметно:

1. Что изменено и зачем.
2. Какие важные файлы/подсистемы затронуты.
3. Какие команды и проверки реально выполнены и каков результат.
4. Что осталось непроверенным или не реализованным.
5. Какие намеренные отличия от оригинала добавлены.

Не называй задачу полностью завершённой, если остались известные пробелы или не выполнены обязательные проверки.
