# Инструкции для ИИ-агентов

Общие правила этого репозитория для Claude Code, Codex, OpenCode и других агентов. Не дублируй их в инструментальных файлах. `CLAUDE.md` должен импортировать этот файл.

## Проект и стек

Thaumic Horizons: Reforged — порт Thaumic Horizons из Minecraft 1.7.10 на современный Minecraft/NeoForge как дополнение для Thaumcraft 4: Reforged (TC4R).

- Текущая цель: Minecraft 26.3, NeoForge 26.3.0.57-beta, Java 25. Перед работой сверяй версии в `gradle.properties`.
- TC4R — обязательная зависимость. Локальная сборка использует sibling-репозиторий через `includeBuild('../thaumcraft-4-reforged')` в `settings.gradle`; CI проверяет закреплённую ревизию в `.github/workflows/ci.yml`.
- Основные слои: `src/main/java/dev/visfox/thaumichorizons/`, `src/main/java/dev/visfox/thaumichorizons/platform/`, `src/main/java/dev/visfox/thaumichorizons/client/platform/`, `src/main/java/dev/visfox/thaumichorizons/compat/` и `src/main/java/dev/visfox/thaumichorizons/compat/tc/`.

## Источники истины и приоритет

Для конкретного изменения используй такой порядок:

1. Явное требование пользователя.
2. Подтверждённое намеренное отличие, зафиксированное в `docs/fidelity.md`.
3. Оригинальная реализация и ресурсы в `reference/1.7.10/` — источник игрового поведения, чисел, рецептов, аспектов, исследований и ассетов.
4. Закреплённый исходный код TC4R — источник API и правил интеграции. Старые ID предметов и блоков сопоставляй через `../thaumcraft-4-reforged/tools/data/id_map.json`; не угадывай современные ID по названию.
5. Существующий код и документация репозитория — источник текущих соглашений и реализации, но не доказательство оригинального поведения.

Назначение документов:

- `docs/fidelity.md` — подтверждённые намеренные отличия и известные неполные порты.
- `docs/verification.md` — только реально выполненные проверки.
- `docs/roadmap.md` — план, который может отставать от кода и CI.
- `docs/architecture.md` и `docs/tc4r-integration.md` — архитектурные и TC4R-контракты.

Если источники расходятся, не выбирай поведение по памяти. Проверь реализацию и документацию, явно сообщи о неподтверждённом API или поведении и не маскируй отсутствие реализации заглушкой. Необходимые исправления подтверждённых багов документируй в `docs/fidelity.md`.

## Команды

Запускай команды из корня репозитория. На Windows используй `python` и `gradlew.bat`; на Unix — `python3` и `./gradlew`.

- Автоматические проверки: `python -I tools/check_seams.py`
- Проверка части ссылок на ассеты: `python -I tools/check_assets.py`
- JUnit: `gradlew.bat test`
- Сборка: `gradlew.bat build`
- Клиент: `gradlew.bat runClient`
- Dedicated server: `gradlew.bat runServer`

Для Unix замени `python` на `python3`, а `gradlew.bat` на `./gradlew`. Выбирай самую узкую проверку, покрывающую изменение; полную сборку запускай, когда она необходима для приёмки.

## Работа с задачей

- Перед изменениями проверь ветку, HEAD и `git status`. Сохраняй чужие и пользовательские незакоммиченные изменения; не переформатируй весь файл ради локальной правки.
- Изучай только части проекта, относящиеся к задаче. Для портирования игровой механики сверяй оригинальную реализацию и связанные регистрации, рецепты, исследования, аспекты, локализацию и ассеты. Для документации и небольших инструментальных задач не обходи весь проект.
- Прослеживай клиентскую/серверную сторону, сохранение, синхронизацию и multiplayer там, где это затрагивается.
- Используй существующие registry-классы, attachments, data components, codecs и рецептурные системы. Не создавай второй источник истины для уже существующей механики.
- Не добавляй заглушки, placeholders, guessed mappings или фальшивые fallback-пути.

## Архитектурные границы

Есть две независимые границы совместимости:

- `src/main/java/dev/visfox/thaumichorizons/platform/` и `src/main/java/dev/visfox/thaumichorizons/client/platform/` изолируют различия Minecraft/NeoForge и клиентские платформенные API.
- `src/main/java/dev/visfox/thaumichorizons/compat/` изолирует взаимодействие игровой логики с Thaumcraft/TC4R.

### Всегда

- Не обходи существующие platform seams прямыми импортами версионных API.
- Используй внутренности TC4R через `src/main/java/dev/visfox/thaumichorizons/compat/` и его адаптеры. Прямые импорты допустимы только для классов, явно разрешённых в `THAUMCRAFT_API` внутри `tools/check_seams.py`.
- Размещай реализацию TC4R и её mixin-цели в `src/main/java/dev/visfox/thaumichorizons/compat/tc/`, а не в gameplay-коде.
- Не позволяй общему/server-коду ссылаться на client-only классы.
- Перед изменением TC4R-интеграции прочитай `docs/tc4r-integration.md`.

### Сначала предложи узкий контракт

- Не расширяй allowlist TC4R API ради удобства. Сначала проверь, можно ли добавить узкий compat-интерфейс; обоснование расширения документируй в `docs/tc4r-integration.md`.
- Не изменяй sibling-репозиторий TC4R без прямого разрешения пользователя.
- Не добавляй новую зависимость без прямого разрешения пользователя.

### Никогда

- Не импортируй внутренности TC4R напрямую из gameplay-кода.
- Не создавай placeholder-ассеты или guessed mappings, чтобы скрыть отсутствующий ресурс.
- Не выдавай сборку, JUnit, seam check или CI за игровое тестирование.

Подробности: `docs/architecture.md` и `docs/tc4r-integration.md`.

## Код и ресурсы

- Следуй стилю соседнего кода; отступы Java и Python — 4 пробела. Комментарии нужны для причин, инвариантов и неочевидных ограничений, а не для пересказа кода.
- Не создавай ItemStack с data components до их привязки через `DefaultDataComponentsBoundEvent`; используй ленивое создание по существующему образцу.
- Соблюдай уникальность registry IDs, recipe keys, payload IDs, research keys и resource locations.
- Пути ресурсов — lowercase. При изменении ассетов проверяй blockstates, модели, parents, текстуры и ссылки между ними.
- Поддерживай `en_us` и `ru_ru`; проверяй локализационные ключи по API, который их формирует.

## Проверки

- JUnit 5 подходит для детерминированной логики, codecs, сериализации, преобразований данных и fallback-контрактов.
- Не добавляй NeoForge GameTest автоматически; сначала обоснуй, почему сценарий нельзя покрыть существующими средствами.
- `tools/check_seams.py` проверяет настроенные архитектурные границы.
- `tools/check_assets.py` проверяет часть статических ссылок на модели и текстуры; это локальная проверка, не визуальный тест.
- Для multiplayer-механики проверяй сценарий с двумя клиентами. Для сохранения — перезагрузку мира после взаимодействия. Не называй выполненной проверку, которую не запускал.
- Обновляй `docs/verification.md` только по фактическим результатам, а `docs/fidelity.md` — при подтверждённых отклонениях от оригинала.

## Git и совместная работа

- Не перезаписывай чужие изменения, не переписывай историю и не удаляй незнакомые файлы.
- Не делай force-push, не удаляй ветки/теги и не меняй настройки репозитория без прямого разрешения.
- Не отправляй изменения в удалённый репозиторий и не создавай/обновляй PR или релизы, пока пользователь явно не разрешил соответствующее действие. Прямое одобрение конкретного плана достаточно: не запрашивай повторное подтверждение того же действия. Merge — отдельное действие, требующее отдельного разрешения.
- Коммиты — на английском, в стиле Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`).
- При параллельной работе разделяй ответственность и файлы. Согласуй изменения общих интерфейсов, registry-классов, mixin-конфигурации и build-файлов; проверь diff агентов до интеграции.

## Отчёт

Укажи, что изменено, какие проверки действительно выполнены, что осталось непроверенным и какие намеренные отличия от оригинала появились. Не называй задачу полностью завершённой, если остались известные пробелы.
