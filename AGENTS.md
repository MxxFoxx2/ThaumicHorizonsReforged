# Инструкции для ИИ-агентов

Общие правила этого репозитория для Claude Code, Codex, OpenCode и других агентов. Не дублируй их в инструментальных файлах.

## Проект и источники истины

Thaumic Horizons: Reforged — порт Thaumic Horizons из Minecraft 1.7.10 на современный Minecraft/NeoForge как дополнение для Thaumcraft 4: Reforged (TC4R).

- Оригинальное поведение сверяй с `reference/1.7.10/`; не восстанавливай механику по памяти или догадке.
- Старые ID предметов и блоков сопоставляй через TC4R `tools/data/id_map.json`, если он доступен. Не угадывай современные ID по названию.
- `docs/fidelity.md` описывает намеренные отличия и известные неполные порты.
- `docs/verification.md` фиксирует реальные результаты проверок.
- `docs/roadmap.md` описывает план, но может отставать от кода и CI.
- Актуальные версии Minecraft, NeoForge и Java бери из `gradle.properties`.

Сохраняй поведение, числа, рецепты, аспекты, исследования и ассеты оригинала. Необходимые исправления багов документируй в `docs/fidelity.md`.

## Работа над задачей

- Перед изменениями проверь ветку, HEAD и `git status`. Сохраняй чужие и пользовательские незакоммиченные изменения.
- Изучай только те части проекта, которые относятся к задаче. Для портирования игровой механики сверяй оригинальную реализацию и связанные регистрации, рецепты, исследования, аспекты, локализацию и ассеты. Для документации и небольших инструментальных задач не нужно обходить весь проект.
- Прослеживай клиентскую/серверную сторону, сохранение, синхронизацию и multiplayer там, где это затрагивается.
- Если API, исходник или поведение не удалось подтвердить, явно укажи это. Не придумывай совместимость и не маскируй отсутствие реализации заглушкой.

## Архитектурные границы

Есть две независимые границы совместимости:

- `platform/` и `client/platform/` изолируют различия Minecraft/NeoForge и клиентские платформенные API.
- `dev.visfox.thaumichorizons.compat/` изолирует взаимодействие игровой логики с Thaumcraft/TC4R.

Обязательные правила:

- Не обходи существующие platform seams прямыми импортами версионных API. Границы проверяет `tools/check_seams.py`.
- Внутренности TC4R используй через `compat/` и его адаптеры. Прямые импорты допустимы только для классов, явно разрешённых в `THAUMCRAFT_API` внутри `tools/check_seams.py`.
- Не расширяй allowlist ради удобства: сначала проверь, можно ли добавить узкий compat-интерфейс. Обоснование расширения документируй в [tc4r-integration.md](docs/tc4r-integration.md).
- Реализация TC4R и её mixin-цели находятся в `compat/tc/`; не размещай их в gameplay-коде.
- Общий/server-код не должен ссылаться на client-only классы.
- Используй существующие registry-классы, attachments, data components, codecs и рецептурные системы. Не создавай второй источник истины для уже существующей механики.

Подробности: [architecture.md](docs/architecture.md) и [tc4r-integration.md](docs/tc4r-integration.md).

## Код и ресурсы

- Следуй стилю соседнего кода; отступы Java и Python — 4 пробела. Комментарии нужны для причин, инвариантов и неочевидных ограничений, а не для пересказа кода.
- Не создавай ItemStack с data components до их привязки через `DefaultDataComponentsBoundEvent`; используй ленивое создание по существующему образцу.
- Соблюдай уникальность registry IDs, recipe keys, payload IDs, research keys и resource locations.
- Пути ресурсов — lowercase. При изменении ассетов проверяй blockstates, модели, parents, текстуры и ссылки между ними.
- Не добавляй placeholder-ассеты или guessed mappings, чтобы скрыть отсутствующий ресурс.
- Поддерживай `en_us` и `ru_ru`; проверяй локализационные ключи по API, который их формирует.

## Проверки

Выбирай проверки по затронутой части проекта:

- JUnit 5 подходит для детерминированной логики, codecs, сериализации, преобразований данных и fallback-контрактов.
- Не добавляй NeoForge GameTest автоматически; сначала обоснуй, почему сценарий нельзя покрыть существующими средствами.
- `python3 -I tools/check_seams.py` проверяет настроенные архитектурные границы.
- `python3 -I tools/check_assets.py` проверяет часть статических ссылок на модели и текстуры; это локальная проверка, не визуальный тест.
- `./gradlew test` и `./gradlew build` запускают соответствующие автоматические проверки и сборку.
- Dedicated server, client и multiplayer подтверждают только сценарии, которые действительно были запущены и воспроизведены.

Не выдавай сборку, JUnit, seam check или CI за игровое тестирование. Обновляй `docs/verification.md` только по фактическим результатам, а `docs/fidelity.md` — при подтверждённых отклонениях от оригинала.

## Git и совместная работа

- Не перезаписывай чужие изменения, не переписывай историю и не удаляй незнакомые файлы.
- Не делай force-push, не удаляй ветки/теги и не меняй настройки репозитория без прямого разрешения.
- Не отправляй изменения в удалённый репозиторий и не создавай/обновляй PR или релизы, пока пользователь явно не разрешил соответствующее действие. Прямое одобрение конкретного плана достаточно: не запрашивай повторное подтверждение того же действия. Merge — отдельное действие, требующее отдельного разрешения.
- Коммиты — на английском, в стиле Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`).
- При параллельной работе разделяй ответственность и файлы. Согласуй изменения общих интерфейсов, registry-классов, mixin-конфигурации и build-файлов; проверяй diff агентов до интеграции.

## Отчёт

Укажи, что изменено, какие проверки действительно выполнены, что осталось непроверенным и какие намеренные отличия от оригинала появились. Не называй задачу полностью завершённой, если остались известные пробелы.
